USDT Wallet Architecture — 3 Approaches

BSC (BEP20) USDT replaces Stripe token purchases

New Token Flow: USDT → Wallet → Credits
The Concept:
1. User gets unique BSC deposit address
2. User sends USDT (BEP20) from MetaMask / exchange
3. Wallet Service detects deposit on-chain
4. Main API credits wallet_usdt_balance
5. User converts USDT → Platform Tokens (1:1) = "gas" for bot fees
6. On winning trade: 20% fee deducted from token balance
7. User can withdraw USDT anytime (wallet → their external address)
A

Monolithic Integrated Wallet

All wallet logic lives inside the main Hono API. One central BSC hot wallet. Users deposit to it and attach a unique deposit code (e.g., send $50.23) so we know who it belongs to. API polls BscScan.

Pros

  • No extra service to run
  • Simple local dev
  • One codebase

Cons

  • Deposit matching is fragile (users forget code, send wrong amount)
  • All custody risk in one process
  • Hard to scale blockchain monitoring
  • No clean separation of concerns
B

Dedicated Wallet Service + HD Addresses

Separate Wallet Service generates unique BSC addresses per user from a master HD seed. Monitors blockchain via WebSocket/BscScan. Notifies Main API on confirmed deposits. Handles sweeping + withdrawals independently.

Pros

  • Clean separation — blockchain logic isolated
  • Unique addresses = no deposit confusion
  • Can scale independently (more workers for monitoring)
  • Main API doesn't hold blockchain keys
  • Industry standard approach

Cons

  • Need to manage BNB gas for sweeping/withdrawals
  • Two services to run in dev
  • Slightly more infra complexity
C

Smart Contract Deposit Gateway

Deploy a BSC smart contract that users deposit USDT into. Contract emits Deposit(userId, amount) events. Wallet Service listens to events. No address generation, no sweeping, one contract for all.

Pros

  • No per-address gas costs
  • No HD key management
  • Deposits are self-identifying via contract events
  • One address to communicate to users

Cons

  • Requires smart contract development + audit ($$$)
  • Users need to interact with contract (approve + call) — more complex than simple transfer
  • Contract bug = catastrophic loss
  • Slower to iterate than backend-only

My Recommendation: Approach B

For a trading bot platform, Approach B (Dedicated Wallet Service + HD Addresses) hits the sweet spot. It gives you clean separation without the cost/risk of smart contract development. Here's the high-level flow:

  • Wallet Service runs as a separate Node.js process (could also be Hono) with its own config.
  • Uses bip32/bip39 to derive BSC addresses from a master seed. Each user gets a unique index.
  • Monitors USDT Transfer events on BSC via WebSocket connection to a BSC node (or QuickNode/Ankr) + BscScan API fallback.
  • After 12 block confirmations, sends deposit notification to Main API via Redis Pub/Sub or internal HTTP.
  • Sweeping: Periodically consolidate deposit addresses to a central hot wallet. Only sweep if balance > gas cost threshold (e.g., >$1). Keeps dust manageable.
  • Withdrawals: Main API requests withdrawal → Wallet Service signs tx from hot wallet (holds BNB for gas).
  • Token conversion: 1 USDT = 1 Token (fixed). Deposit auto-converts, or user converts manually via UI. Tokens are just internal ledger entries.
