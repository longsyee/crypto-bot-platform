Data Flow & Edge Cases

How orders, signals, and errors move through the system

Signal Bot Flow
1. TradingView Webhook → POST /webhooks/signal/:botId (HMAC verified)
2. API validates bot ownership, mode (paper/live), token balance ≥ projected fee
3. API enqueues "signal-execute" job to BullMQ (Redis)
4. Bot Worker picks up job → loads bot config + encrypted exchange keys
5. Worker calls CCXT → places market/limit order on exchange
6. On fill: Worker calculates PnL, deducts 20% token fee if winner
7. Worker writes to bot_orders + bot_logs + Redis Pub/Sub event
8. API forwards event via SSE to user's frontend dashboard
DCA Martingale Bot Flow
1. User starts bot via API → enqueues "dca-start" job
2. Bot Worker spawns a persistent loop for this bot
3. Loop polls CCXT WebSocket/ticker for configured symbol
4. On trigger condition (price drop %, time interval, etc.) → place safety order
5. Track filled base orders + safety orders; recalculate take-profit target
6. On full fill at take-profit: realize PnL, deduct 20% fee if winner
7. If max martingale levels reached without profit: stop bot + alert user
8. All states synced to DB; events streamed via Redis Pub/Sub
Error Handling & Edge Cases
Exchange API Failure: Retry with exponential backoff (max 3 retries). If persistent, pause bot + alert.

Rate Limit Hit: Worker reads CCXT rate limit headers; throttles dynamically. Queues jobs with delayed delivery.

Insufficient Token Balance: Bot auto-pauses BEFORE placing order. Dashboard shows "Top up required". Paper mode unaffected.

Invalid Webhook Secret: Reject with 401. Log to security_events table (audit trail for abuse).

Bot Crash / Worker Restart: On startup, worker reconciles: reads all bots with status='running' from DB, resumes their loops. Uses DB as source of truth.

Paper Mode → Live Mode Toggle: Changing mode flushes paper_trades to a summary record ("session report"), resets unrealized PnL. Prevents mixing.

Exchange Connection Invalid: CCXT "Invalid API key" → mark connection as `is_active=false`, notify user to re-verify.

Duplicate Order Prevention: Worker uses idempotency key (botId + signalId + timestamp) in bot_orders to prevent double-execution from webhook retries.

Referral Loop Prevention: User cannot refer themselves. `referred_by` FK + unique constraint prevents circular references.

Admin Kill Switch: Admin endpoint `POST /admin/bots/:id/emergency-stop` bypasses normal queues, force-stops bot loop + cancels open orders via CCXT.
